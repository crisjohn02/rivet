T31 — Make refresh safe under concurrency, races and interruption, and make every query read one committed snapshot.

What the documents require, and what the code does today:

1. The writer lock is taken FIRST. The pseudocode begins with `begin immediate transaction (busy timeout: 5 seconds)`, then loads the inventory, walks, reads, parses, replaces facts, re-resolves, rechecks, and commits, all inside that one transaction. ARCHITECTURE: "Parse inside the writer transaction in the simple first implementation; this can hold the writer slot longer but prevents competing refreshes from publishing out of order." Today `refresh.rs` reads the previous inventory, walks and parses OUTSIDE any transaction, and only `publish_inventory` opens `BEGIN IMMEDIATE`. Two concurrent refreshes can therefore each compute from the same old inventory and publish out of order, so an older scan of the working tree can overwrite a newer one. Use-id assignment from a high-water mark read outside the transaction is exposed to the same race. Move the whole refresh inside the writer transaction.
2. A lock that cannot be acquired within the busy timeout is `repository_unavailable`, exit 3, with a message naming the lock. It must never fall back to answering from the existing snapshot: "Default refresh failures do not fall back to cached answers." Only an explicit `--no-refresh` reads the cache.
3. Race detection. Spec §12.4 step 3: "Recheck observed file metadata and the eligible path set before commit. Retry the whole refresh once on a detected race; continued mutation returns `repository_changed` (exit 9)." Recheck before commit that every file read still has the metadata observed when it was read, and that the eligible path set is unchanged. On a mismatch, roll back and retry the whole refresh exactly once; a second mismatch is exit 9.
4. Cancellation. "A crash or cancellation before commit rolls back the refresh." A process killed mid-refresh must leave the previous complete snapshot intact, a database passing `PRAGMA integrity_check`, and a next refresh that succeeds.
5. Snapshot-consistent reads, the audit's first unverified suspicion. Spec §12.4 step 4: "Read all query data and source from one committed snapshot." ARCHITECTURE: "Readers use a committed read transaction." Today each `Store` read opens its own transaction, so a query that reads uses and then bindings can straddle another process's publish, and a reused `use_id` could pair a binding with the wrong use. Make each query perform all its reads, including the source bytes it slices and the snapshot digest it reports, inside one read transaction. The `index.snapshot` digest in a response must be the digest of the snapshot its data was actually read from, not of an earlier one.
