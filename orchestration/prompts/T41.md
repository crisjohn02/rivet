## Context

The user has decided to start TypeScript support now. This overrides Gate G's deferral: record
that in the checkpoint. T41 is the first of a chain, and T42 extracts definitions. So T41 must
**not** change what the CLI reports for `.ts` and `.tsx` files. They stay counted and diagnosed as
`unsupported_language` until an extractor exists. Calling a file indexed while extracting nothing
from it would be dishonest.

## Build

### 1. Grammar dispatch (`rivet-parser` / `rivet-languages`)

- **Grammars.** `.ts`, including `.d.ts`, parses with the TypeScript grammar, and `.tsx` with the
  TSX grammar, from the pinned `tree-sitter-typescript`.
  - Expose this through the existing grammar surface: `LanguageId::Typescript` and
    `LanguageId::Tsx`.
  - Add a single, documented switch that says whether a language has an extractor. It is `false`
    for TypeScript in this task, and the CLI must consult it, so that T42 flips it in one place.
- **Unsupported extensions.** `.js`, `.jsx`, `.mjs`, `.cjs`, `.mts`, `.cts` and `.d.mts` stay
  unsupported, as today. Add a test that pins this list, including `.mts`/`.cts`, which the
  TypeScript grammar could parse but v0.1 does not claim.
- **Parse policy.** The same v0.1 rule as PHP applies, at the parser level: a tree containing
  `ERROR` or missing nodes is a parse failure. Add parser tests for:
  - a valid `.ts` file, a valid `.tsx` file with JSX, and a valid `.d.ts` file;
  - a `.ts` file containing JSX, which must fail under the TS grammar (it is not TSX);
  - a genuinely broken file.

  Do not wire parse results into the index yet.

### 2. Authored fixture (`tests/fixtures/typescript/`)

Write a small, readable fixture project of about 8–12 files. It must exercise every construct
ADDING-A-LANGUAGE's TypeScript column names, so T42–T45 can verify against it. Put an inline
`// gold:` marker style or comments like the PHP fixture where that helps. Cover:

- **Definitions:**
  - functions, including overload signatures;
  - classes with methods, fields, constructors with parameter properties, static and abstract
    members, and getters and setters;
  - interfaces, enums (regular and `const`), namespaces and `module` blocks;
  - named `const` bindings to arrow and function expressions, which are one `function` symbol
    each, not a duplicate const;
  - plain named consts.

  Type aliases and generics are listed separately so that T42 can decide explicitly; the doc's
  column does not name type aliases (see Contradictions).
- **Anonymous containers:** default-exported anonymous function/class, IIFE, callbacks. Uses
  inside attach to the nearest named container or null.
- **Uses:**
  - calls, `new`, member calls on `this`, a `new` receiver and annotated receivers (parameter,
    field, variable);
  - type positions;
  - top-level uses;
  - template-literal interpolation;
  - shadowing, where a local of the same name as an import is used;
  - optional chaining.
- **Imports and exports:**
  - direct relative named, default and aliased imports;
  - namespace imports used as `ns.member`;
  - re-exports, `export *`, a path alias like `@/x`, a package import, `require`, and `import type`.
    These must stay unresolved in later tasks.
  - an ambiguous relative path, for example both `x.ts` and `x/index.ts`, to exercise the ordered
    candidate rule.
- **TSX:**
  - capitalized component names as uses;
  - lowercase intrinsic elements, which are not uses;
  - JSX expression containers;
  - literal JSX text containing identifier-like words, which is excluded;
  - fragments;
  - component props.
- **Declaration files:** a `.d.ts` file with ambient declarations.
- **Parse failures:** one intentionally broken `.ts` file.
- **Unsupported:** one `.js` file and one `.mts` file.

### 3. Gold (`tests/gold/typescript-authored.toml`)

- **What the gold holds.** Hand-authored expectations for declarations, with their spans, kinds and
  qualified names, and for uses at the level ADDING-A-LANGUAGE defines. Follow the PHP gold's span
  conventions, adapted:
  - declarations start at the first modifier or keyword, including `export`. Decide this, and
    document it in the gold file's header.
  - uses cover the identifier only.
- **How it is established.** Gold must come from the TypeScript grammar and your reading, not from
  rivet, which has no extractor yet. Mechanical span computation is fine, for example a script that
  finds marker text in the fixture, as the PHP gold did. Record how it was generated.
- **Pending entries.** Tag each entry with the task that makes it verifiable, T42, T43, T44 or
  T45, and extend `check_gold.py` accordingly:
  - it verifies only entries whose task is marked done in one explicit list in the gold file;
  - it prints the count of pending entries per task, for example
    `pending 37 typescript entries (T42: 20, T43: 12, T44: 5)`;
  - it never skips entries silently.
- **Current checker behaviour.** With no TypeScript task done, `check_gold.py` still verifies the
  51 PHP entries, reports every TypeScript entry as pending, and exits 0.
- **Span self-check.** Add one that needs no rivet: every TypeScript gold span's recorded `text`
  matches the fixture bytes at that span.
