T25a — Correct the collapsed container form.

`signature_summary` currently produces this for the `Members.php` fixture, and its own unit test asserts it as correct:

```text
abstract class AbstractThing
{
    public const FIRST = 1, SECOND = 2;
    public const FIRST = 1, SECOND = 2;
    public static int $count = 0;
    public readonly string $title;
    public int $left, $right = 2;
    public int $left, $right = 2;
    abstract public function describe(): string { … }
    public function __construct(private int $seed, public string $tag = 'x') { … }
    private int $seed;
    public string $tag = 'x';
}
```

Three faults, all of which defeat the purpose spec §16.2 gives the collapsed form, namely telling an agent what exists and how to call it at a fraction of the cost of the body:

1. A multi-name declaration renders the whole shared declaration once per declared name, so the constant and property lines each appear twice. Worse, the second element's own `signature` field names the first element.
2. A bodyless declaration renders with ` { … }`, so an abstract method and an interface method both claim a body they do not have.
3. A promoted constructor property appears three times: inside the constructor's signature, and again as a standalone member per parameter.

Requirements:

1. Per-name signatures. Each symbol's own `signature` must describe only that name. `$right` renders `public int $right = 2`, not `public int $left, $right = 2`. Same for constants. This changes the stored per-symbol `signature`, not only the summary, so state clearly which symbols' stored signatures change and confirm the gold declaration spans are unaffected, since `text` in gold is source bytes and must not move.

2. No body marker on a bodyless declaration. An abstract method, an interface method, and any other declaration with no body render without ` { … }`. A method with a body keeps it.

3. Settle the promoted-property duplication with a stated rule. Either list promoted properties as members and leave them out of the rendered constructor signature, or keep them in the constructor signature and do not list them separately. Pick one, implement it, and justify it in your report. Listing them in both places is the one option to reject. Whichever you pick, a promoted property remains an addressable symbol; this is about the summary text only, not about extraction.

4. Do not change what is extracted. T25's symbols, kinds, qualified names, parents and gold entries are correct and must not move. `python3 tests/gold/check_gold.py` must still report 51 entries. If your change would alter a gold span, stop and report rather than editing gold.

5. Update the tests that currently assert the wrong output. `signature.rs`'s summary tests encode all three faults as expected values; rewrite those expectations to the corrected form rather than deleting the tests. Add a test for an interface summary proving no member carries a body marker.
