## Why

The harness only accepts `kind = "pilot"` and reports no intervals. The
user has approved a held-out study with these parameters:

- 20 tasks on the held-out PHP project, 5 trials, arms B and C, $60 cap.
- **Efficiency gate:** the upper one-sided 95% bound on C/B must be below 1.00.
- **Quality gate:** the lower one-sided 95% bound on success C − B must be above
  −5 percentage points.

This task builds the machinery. The tasks themselves and the preregistration
are separate tasks.

## Build

### 1. `kind = "confirmatory"` in `study.toml`

It keeps every pilot rule and adds a required `[confirmatory]` table:

```toml
[confirmatory]
preregistration = "benchmark/preregistration.md"   # repo-relative
preregistration_sha256 = "<64 hex>"
rivet_binary_sha256 = "<64 hex>"
tasks_sha256 = "<64 hex>"         # see below
analysis_version = "t48a-1"
analysis_seed = 20260927          # integer
bootstrap_replicates = 10000      # integer >= 1000
min_complete_trials_per_task = 3  # integer >= 1, <= trials
max_excluded_block_fraction = 0.10  # in [0, 1)
```

- **`arms`:** must be exactly `["B", "C"]`.
- **`tasks_sha256`:** the SHA-256 of the UTF-8 text made of one line per
  file, `<task-id>/<relative path>\t<sha256 of the file bytes>\n`. It covers
  every regular file under each listed task directory, sorted by that
  path's bytes. The text contains no absolute paths. Implement it once in
  `study.py`, and add a `run_study.py hash-tasks <study>` command that
  prints it.
- **Refusals.** `validate`, `plan` and `run` must refuse a confirmatory study
  unless all of these hold:
  - the preregistration file exists and its SHA-256 matches;
  - the file is tracked by git and unmodified relative to `HEAD`, checked
    with `git` in the repository that holds the manifest;
  - the listed tasks hash to `tasks_sha256`.
- **`run` only:** it additionally refuses unless
  `RIVET_PILOT_RIVET_BIN` hashes to `rivet_binary_sha256`.
- **Refusal messages** say which check failed and print both hashes.
- **Dry runs.** When `RIVET_PILOT_CLAUDE_BIN` is overridden, every record is
  marked as a dry run. For a confirmatory study, the runner then requires
  `--dry-run` on the command line, and `report.py` refuses to compute gates
  from any dry-run row. It labels such a report DRY RUN in its title and does
  not evaluate the gates. That lets the no-model rehearsal use the real
  manifest and tasks without ever passing for a result.

### 2. Confirmatory analysis in `report.py`

It applies when the manifest is confirmatory. Pilot output must stay
byte-identical for the existing pilot fixtures.

- **Inclusion.** Follow the frozen retry rule already implemented by
  `extract.py`:
  - Failures of any kind (timeout, crash, invalid answer, limit reached)
    count as `pass = 0`, with their consumed tokens.
  - A task/trial block is *excluded* if, after its single allowed rerun,
    either arm lacks an includable attempt. That covers an infrastructure
    failure, missing usage, or contamination (a B run that executed rivet,
    under the existing rule). An excluded block is excluded from **both**
    arms.
  - Report every excluded block with its reason.
- **Validity.** The outcome is `invalid` and no gate is evaluated when any of
  these holds. Name the reason.
  - Some task has fewer than `min_complete_trials_per_task` included blocks.
  - Excluded blocks exceed `max_excluded_block_fraction` of scheduled blocks.
  - A dry-run row is present.
  - `analysis_version` differs from the script's own constant.
- **Point estimates** use equal task weighting over included blocks:
  - `ratio` = mean over tasks of (task mean C tokens) ÷ mean over tasks of
    (task mean B tokens). Tokens are `input_tokens_total`.
  - `success_diff_pp` = 100 × (mean over tasks of the C pass rate − mean over
    tasks of the B pass rate).
- **Paired cluster bootstrap.**
  - `random.Random(analysis_seed)`, `bootstrap_replicates` replicates.
  - Each replicate resamples tasks with replacement *within language strata*.
    The language is the task project's `languages` in `benchmark/corpus.toml`.
    A project with more than one language is an error for now. Keep each
    stratum's size.
  - Each draw brings all of that task's included blocks, both arms.
  - Recompute the two point estimates per replicate.
  - Draw order: iterate strata in sorted name order, and draw by index into
    the stratum's task list sorted by task ID. Write this down in
    TASK-FORMAT.md so the result can be reproduced by hand.
  - **Upper bound on the ratio:** sort the replicate ratios ascending and
    take the value at index `ceil(0.95 × R) − 1`.
  - **Lower bound on the success difference:** sort ascending and take the
    value at index `ceil(0.05 × R) − 1`.
  - **Zero B denominator in a replicate:** that replicate's ratio is `+inf`,
    which is conservative. Count and report such replicates. If the point
    estimate's own denominator is 0, the outcome is `invalid`.
- **Gates and outcome.**
  - `quality_pass` = lower bound > −5.0.
  - `efficiency_pass` = upper bound < 1.00.
  - **Outcome:**
    - `invalid` under the validity rules above;
    - else `fail_quality` when quality fails;
    - else `inconclusive` when efficiency fails;
    - else `pass`.
  - Write the outcome, bounds, point estimates, replicate count, seed,
    analysis version and exclusion list to `summary.json`, and fill the
    template's gate rows. The template currently says "not computed
    (pilot)". Use the template's existing wording where it fits. Where the
    template's efficiency row still says ≤ 0.70, the confirmatory manifest's
    gate wins, and the report must say which gate was evaluated. Add an
    `efficiency_gate` field to `[confirmatory]`, with only the value
    `"upper_bound_below_1"` allowed for now.
- **Secondary results, point estimates only, labeled secondary:**
  - the successful-run-only token ratio;
  - cost, tool calls and wall-clock ratios;
  - per-task and per-category tables;
  - adoption and fallbacks.

## Tests (synthetic, in `test_runner.py` or a new test module)

BENCHMARK.md lists the cases. All are required:

- a known token ratio, with a hand-computed expected ratio and bounds on a
  tiny fixture with a small `bootstrap_replicates`;
- unequal trial counts per task;
- a cheaper failed run, which is counted;
- a retry, where the rerun replaces the block and is not double-counted;
- missing usage, which excludes the block from both arms;
- a zero denominator in a replicate, and in the point estimate;
- incomplete arm blocks;
- each outcome branch: `pass`, `fail_quality`, `inconclusive`, and `invalid`
  for each validity reason;
- the same inputs and seed produce byte-identical `summary.json`, and a
  different seed changes the bounds but not the point estimates;
- two strata keep their sizes;
- every refusal in section 1: a preregistration hash mismatch, an untracked
  or modified preregistration, a task-hash mismatch, a binary-hash mismatch,
  and an override without `--dry-run`;
- a dry-run report is labeled and evaluates no gate.

Run the existing runner tests too; the pilot behaviour must not change.
