T35 — Select and pin the real benchmark repositories, record their licences, and add a small hand-verified PHP gold sample outside the authored fixture. This task selects and records; it runs no benchmark. T37 will measure rivet on what you pin.

Constraints that override everything below:
- Never execute anything from a candidate repository: no install step such as `composer install` or `npm install`, no scripts, no hooks, no tests. The T35 row says "Do not execute arbitrary setup scripts during selection". Cloning and reading files is allowed.
- Never commit a candidate repository's code into this repository. Record pins in a manifest, fetch into a git-ignored directory, and commit only the manifest, the fetch script, notes and gold data.
- The rivet binary must still need no network. Network use here is yours during selection, and the fetch script's, never the binary's.

Requirements:

1. Selection criteria, from `docs/BENCHMARK.md`: at least one real PHP project and one real TypeScript or TSX project, each under a permissive licence (MIT, BSD, Apache-2.0 or similar; no GPL, AGPL, SSPL, Elastic or source-available licences), each with a reproducible test suite, pinned to an exact commit. Prefer at least one project unlikely to have been memorized by models, noting that "low popularity alone does not establish that".
2. The PHP project is what T37 will measure, so choose it for fit with what rivet supports today:
   - modern namespaced PHP that the extractor handles, per the MVP support boundary;
   - a realistic size, on the order of hundreds to a few thousand PHP files, large enough that index timing means something and small enough to index in seconds;
   - common method names shared across classes, since the T35 row requires that "the PHP fixture exercises common method names" such as `handle`, `get` or `save`, which exercise ambiguity and name-only matching.
   Report each candidate's file count and how many of its files rivet indexes versus skips, measured by running the current rivet binary on a clone. That is rivet reading the code, not the code running.
3. TypeScript extraction does not exist yet; it is deferred behind Gate G. Pin the TypeScript project anyway, as the benchmark requires both, and state that it cannot be measured until T41 onward.
4. Licence verification. For each chosen project, read the licence file at the pinned commit itself, not only the repository's front-page badge, and record the SPDX identifier, the licence file path, and the copyright line. If the licence text and the badge disagree, reject the project.
5. The manifest. Create `benchmark/corpus.toml` recording for each project its name, URL, exact commit SHA, commit date, SPDX licence, licence file path, copyright holder, language, file counts from item 2, the test-suite command you found documented but did NOT run, and a short rationale. Choose the field names, and keep them stable, since later benchmark tasks will read this file.
6. The fetch script. Create `benchmark/fetch-corpus.sh` that clones each project into `benchmark/corpus/<name>/`, checks out exactly the pinned SHA, and verifies that `HEAD` equals it, failing loudly otherwise. It must run nothing from the cloned repository. Add `benchmark/corpus/` to this repository's root `.gitignore`. Running it twice must be safe.
7. Pilot and held-out separation. The T35 row requires that "future held-out tasks remain separate from pilot cases". Decide how to separate them, for example by distinct repositories or by distinct, named subsystems of one repository, record that partition in `benchmark/corpus.toml`, and explain it. Pilot tasks, from T38, may only draw on the pilot partition.
8. The PHP gold sample, outside the authored fixture. In a new `tests/gold/php-real.toml`, record about 10 declarations and about 10 uses from the pinned PHP project, in the same field format as `php-authored.toml`, including the exact first 40 bytes of each span. Choose them to cover at least one method name shared by several classes, one aliased import, one static call through an explicitly named class, and one unresolvable dynamic call. For each use, record the resolution tier you expect from rivet's current rules, reasoning from the rules rather than from rivet's output, so the sample can catch rivet being wrong. Where rivet disagrees with your expectation, say so in your report and do not edit the sample to match.
9. Checking the sample. Extend `tests/gold/check_gold.py`, or add a sibling script, so that the real sample is verified against `benchmark/corpus/<name>/` when it has been fetched, and is skipped with a clear message when it has not. `python3 tests/gold/check_gold.py` must keep working and verifying 51 authored entries with no network and no fetched corpus.
10. Write `benchmark/CORPUS.md`, a short note stating what was chosen and why, the candidates rejected and why, the licence findings, and how to fetch. This is the one documentation file you may create; `docs/` stays untouched except TASKS.md.
11. Run `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test --workspace`, and `python3 tests/gold/check_gold.py`, both before and after fetching the corpus. Paste real results.
